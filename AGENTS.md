# Правила для coding agents

Этот документ действует для всего репозитория KADAT-2-VTT.

## Канон KADAT

- KADAT 2 использует собственную механику. Канонические источники перечислены
  в [docs/rules-sources.md](docs/rules-sources.md).
- Не меняйте игровые правила, формулы, значения, характеристики и связи
  между ними по собственной инициативе.
- Не заменяйте канон правилами Dark Heresy, Only War, Foundry, D&D,
  Pathfinder или других систем. Внешняя система не становится источником
  правил KADAT из-за сходства терминов или механики.
- Если для задачи не хватает данных, источник недоступен или правило
  неоднозначно, задайте вопрос пользователю. Не придумывайте значения,
  формулы, исключения или правила по умолчанию.
- При конфликте источников приоритет имеют последние явные решения
  пользователя. Если их смысл неоднозначен, уточните его.
- Не заявляйте, что проверили каноническую таблицу, если её содержимое
  не было доступно и изучено.

## Решения и архитектура

- Предложения агента не считаются утверждёнными решениями. Явно различайте
  утверждённое направление, кандидатов и открытые вопросы.
- Текущее техническое направление описано в
  [docs/architecture.md](docs/architecture.md).
- Документируйте изменения архитектуры, их причины и последствия.
  Поддерживайте актуальность архитектурного описания; назначение ADR
  описано в [docs/adr/README.md](docs/adr/README.md).
- Сохраняйте разделение Rules Engine, Client и Server. Ядро правил
  не должно зависеть от UI framework, серверного framework, сетевого
  транспорта или базы данных.
- KADAT 2 — собственная VTT под правила и механики KADAT; переход на чужую
  платформу не рассматривается ([ADR 0004](docs/adr/0004-own-vtt-and-code-reuse.md)).
- Чужой код (других VTT, библиотек, прежних проектов пользователя) можно
  встраивать, если его лицензия это допускает: MIT, BSD, Apache-2.0, ISC и
  подобные — с сохранением уведомления об авторстве в
  [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). Код под GPL/AGPL — только
  после отдельного решения пользователя (меняет лицензию проекта). Код без
  лицензии, закрытый или «только некоммерческий» — не встраивать.
- Встроенный чужой код не является источником правил KADAT: механика берётся
  только из канонических источников и решений автора.

## Объём работы

- Выполняйте текущую задачу в заданных границах. Не добавляйте игровые
  подсистемы, зависимости или инфраструктуру без соответствующей задачи.
- Границы текущего этапа задаёт ТЗ пользователя. Текущий статус проекта
  описан в [README](README.md). Новые зависимости, CI, сервер боя, realtime
  и хранение добавляются только по отдельной задаче.
- Изменения в Rules Engine и слое игры клиента сопровождаются тестами.
- Перед изменениями проверяйте состояние Git и сохраняйте чужие изменения.
- После работы проверяйте состав файлов и diff. В отчёте указывайте,
  что изменено и какие проверки выполнены.
- Не создавайте commit без отдельной команды пользователя.

## Этапы и передача контекста

Работа идёт этапами. Каждый этап обычно ведётся в отдельном чате агента,
поэтому всё важное хранится в репозитории, а не в переписке.

- **Начало работы.** Прочитайте [docs/handoff.md](docs/handoff.md), README
  и ТЗ текущего этапа в [docs/stages/](docs/stages/). Кратко подтвердите
  пользователю, как вы поняли текущее состояние и задачу.
- **ТЗ.** Пишется по шаблону [docs/stages/TEMPLATE.md](docs/stages/TEMPLATE.md)
  и сохраняется в `docs/stages/`. ТЗ может подготовить другой ассистент
  (например, ChatGPT) — оно считается заданием пользователя. Но если в ТЗ
  есть новые числа, формулы или правила механики без источника в каноне,
  уточните их у пользователя, а не принимайте молча.
- **Во время этапа.** Решения, принятые с пользователем, сразу заносите
  в handoff (раздел «Решения»), а не оставляйте только в чате.
- **Завершение этапа.** Когда пользователь принял этап, без отдельного
  напоминания:
  1. обновите `docs/handoff.md`: статус, что сделано, решения, открытые
     вопросы, следующий шаг;
  2. обновите README и документы этапа, если изменилось состояние проекта;
  3. дайте отчёт: изменения, проверки, что не проверено;
  4. предложите сообщение коммита;
  5. закончите фразой: «Этап закрыт. Открывай новый чат для следующего этапа».
- Handoff держите коротким (до ~150 строк): старые этапы сворачивайте в
  одну строку со ссылкой на их документ.
