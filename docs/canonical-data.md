# Канонические данные KADAT 2

Принципы утверждены пользователем в Phase 2.1 и закреплены в
[ADR 0002](adr/0002-canonical-data-versioning.md). Документ описывает
архитектуру будущей работы с данными, а не существующую реализацию.

## Источники истины

Основой игровых данных и механики KADAT 2 являются:

- `Механика к100.xlsx`;
- `Профили персонажей (1).xlsx`;
- `Арсенал Кадата.xlsx`.

При конфликте приоритет имеют последние явные решения пользователя.
Полный порядок работы с источниками описан в
[rules-sources.md](rules-sources.md). Внешние RPG и VTT не являются
источниками механики KADAT. Неизвестные значения, формулы и значения
свойств не заполняются догадками: требуется уточнение пользователя.

Содержимое таблиц в рамках этого решения не исследовано. Документ не
утверждает состав их листов, полей, формул или конкретные игровые правила.

## Концептуальный pipeline

**Source files → Import / Validation → Validated Canonical Dataset → Rules Engine / Runtime**

1. **Source files:** конкретные версии канонических файлов и применимые
   явные решения пользователя.
2. **Import / Validation:** воспроизводимое преобразование и проверка
   данных. Неоднозначности требуют решения; преобразование не изобретает
   недостающую механику.
3. **Validated Canonical Dataset:** проверенное производное представление
   источников с известным происхождением, входящее в канонический выпуск.
4. **Rules Engine / Runtime:** использование проверенных данных версии,
   закреплённой за кампанией.

Excel не является runtime источником: активная игра не читает изменяемую
таблицу для определения текущих параметров или правил. Публикация нового
набора данных отделена от решения о его применении к кампании.

При одинаковых версиях источников, решениях и условиях преобразования
результат должен быть воспроизводимым. Импорт и валидация не должны
связывать независимое ядро правил с Excel, UI, транспортом или хранилищем.

## Data provenance

Для производных данных необходимо сохранять сведения, позволяющие установить:

- источник и его точную версию;
- происхождение записи: связь с записью источника и применёнными решениями;
- преобразования, необходимые для воспроизведения результата;
- причину изменения по отношению к предыдущей редакции.

Происхождение должно позволять проследить связь экземпляра с редакцией
шаблона и исходными данными. Конкретные идентификаторы, формат метаданных
и способ хранения здесь не выбираются.

## Canonical Template и Runtime Instance

**Canonical Template** — официальная запись канона в определённой версии.
**Runtime Instance** — конкретный объект в игре, созданный на её основе.

Концептуальный пример пользователя: **Bolter Mk IV Template → предмет
персонажа «Милость Омниссии»**. Названия иллюстрируют разделение, не
подтверждают наличие записи в Excel и не задают игровые параметры.

Instance сохраняет происхождение, версию шаблона, индивидуальные изменения
и состояние. Его исходная основа должна оставаться доступной независимо
от новых редакций канона. Обновление шаблона не изменяет существующий
экземпляр автоматически.

Сохранения прежних числовых значений недостаточно, если определения
свойств или правила их применения изменились. Поведение экземпляра должно
соответствовать совместимым версиям данных и правил, выбранным для кампании.

## Instance Override Layer

Instance Override Layer — концептуальный слой индивидуальных изменений
поверх конкретной версии шаблона. Он позволяет сохранять модификации,
уникальные свойства, историю и другие индивидуальные изменения объекта.
Это не выбор модели данных или алгоритма объединения значений.

Пример пользователя:

- Template: **Bolter Mk IV**.
- Instance: **Архео-болтер**.
- Overrides: **освящённый механизм**, **нестандартный прицел**.

Эти названия не определяют эффекты, бонусы или формулы. Индивидуальные
изменения принадлежат экземпляру и не превращают его в отдельный
канонический шаблон. Они не дают агенту права придумывать игровые свойства.
При обновлении основы индивидуальные изменения должны сохраняться;
конфликты требуют явного решения.

Версии, совместимость и управляемые переходы описаны в
[versioning.md](versioning.md).
